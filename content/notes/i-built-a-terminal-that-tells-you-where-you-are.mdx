I spent a while rebuilding my terminal recently. Not re-theming it. Rebuilding it. New prompt, new listing commands, Neovim and tmux behaviors I'd been meaning to fix for two years. The whole thing lives here: [github.com/Diacod-I/dot-files](https://github.com/Diacod-I/dot-files/tree/main). This post is the reasoning behind it.

## The Core Idea

> Even if a tool looks impressive, it needs to be usable to be considered useful.

A terminal prompt you have to read carefully is a prompt that's failing at its job, and that unfortunately is the case of many terminal themes. So my design goal was simple: surface what's unusual, hide what's normal, and never make me squint my eyes.

This meant pinning down what actually feels unusual and identifying the habits a dev runs on autopilot and only notice when something's off. A few unusual things I found by talking to other devs (some of which I have experienced a lot) were as follows:

1) "Most command outputs feel like a wall of text visually."
2) "I have to use certain git commands unnecessarily just to understand where I am. If I don't, I might end up merging or pushing to the wrong branch."
3) "I get hit with version-number related issues a lot when working with different projects."
4) "Navigation on a terminal takes up a lot of time to get used to. VS Code feels more comfortable in that sense."

### Prompt reacts to context, but presents it better.

I noticed most command prompts and configs dump everything onto one line/row: path, branch, git status, versions, all crammed together, in the same color, whether or not any of it matters right now. It becomes irritating when you have to read left-to-right everytime you want to find a certain detail. 

Realising this, I decided to experiment a "column" format over a row format where each piece of information gets its own row, and rows appear only when they're relevant i.e. when the context is appropriate (Example: There won't be a blank row titled "venv: " when no venv is active at the present). That way it becomes more of a top-to-bottom reading (quick for surface level eyeball comparisons, especially when working with tmux panes). Also, just by adding the respective icons for each detail, all a user needs to do is to search for the icon which contains the detail they want. 

By the way, this "context-based" approach is not new, in fact several popular command line themes use this approach (namely [Oh my ZSH](https://ohmyz.sh/), [powerlevel10k](https://github.com/romkatv/powerlevel10k) and [Starship](https://starship.rs/), the one we are using). It's just that the way we are presenting said context should be accessible much better and quicker from a DX perspective, and a column+icon format that "shows" you what your current scenario is and hence satisfies the conditions for accessibility mentioned before.

The layout I made is as follows:

- The directory row shows the repo-relative path when a user is inside a git repo (Example: \<repo-name\>/path/to/dir) and the path from ~ when they are loose in my filesystem. You never see a wall of absolute path you need to parse mentally everytime you navigate across directories.
- The branch row is a big one. It only appears when inside a repo, and the moment the user is not on main or master, it shows a white-on-red `⚠ OFF-MAIN` flag. This prevents a user from committing to the wrong branch more than once, or wasting my time verifying the current branch with `git branch --show-current` before every commit. The moment a user has uncommited changes, it shows a yellow ` ● UNCOMMITTED` flag to eliminate having to compulsively use `git status` everytime to simply check the presence of unstaged changes. I have also added a delta tracker and a "commits-ahead" tracker to make sure a user knows the local state compared to the remote repo, see how many commits ahead/behind I am from remote, and if there is an artifact not in `.gitignore` that adds thousands of redundant lines of code/text. You know where you are at all times, which dir, repo, branch etc. and every change you make, you just know it.
- The commit row shows the current commit HEAD is on. It shows the shortened commit hash and the one-line commit message. This helps quick eye-balling across tmux panes having different branches, allowing for working on multiple features side-by-side.
- The venv row (as mentioned before) shows only when a `virtualenv` is active. The language rows (`rust`, `py`) auto-hide outside the relevant project.
- Apart from these, there are seperate rows to display version numbers for Python, Rust, Docker etc. on demand based on context. 

The logic of this layout, inevitably, is "if a row is on screen, it's supposed to tell me something about where I am".

This is built with custom starship modules that shell out to git and check the environment per prompt. The off-main-branch flag, for instance, is just:

```bash
b=$(git branch --show-current)
if [ "$b" != main ] && [ "$b" != master ]; then
  printf "%s  \033[1;37;41m ⚠ OFF-MAIN \033[0m" "$b"
else
  printf "%s" "$b"
fi
```


### A rule that brackets every command.

By rule, I dont mean "the law" kinda rule. I mean "a line" kinda rule. A big line. Above each prompt, a full-width horizontal line. It sounds trivial, but it solves a real annoyance I found for command-line only users: scrolling up through a session and not being able to tell where one command's output ends and the next begins. With a rule bracketing every command, that ambiguity disappears. 

The fiddly part was making it resize-safe inside tmux. $COLUMNS doesn't propagate into starship's subshell, and tput cols reports the wrong width inside a tmux pane. The fix was to ask tmux directly:

```bash
w=$(tmux display -p "#{pane_width}" 2>/dev/null || tput cols)
```

tmux always knows its own pane width and updates it live on resize, with tput cols as the fallback for a bare terminal. The rule also carries a per-command counter (#7) that resets with cls. It's a small thing, but it makes "how much have I done in this session" answerable at a glance.

### Listings you can actually scan with a glance.

I have about thirty project folders. A plain `ls` (not even a `ls -R`) of that brings the same text wall problem and is often a nightmare to mentally parse at scale. A few developers I've talked to hit the same lag just parsing a big ls dump.

So, I made custom `ls`/`ll`/`lf`/`lt` commands wrapping `eza`, indented for readability, and an `lf` command, which does something specific. It's a one-per-line view that emphasizes the first letter of each name, so an alphabetical list becomes something my eyes can jump down, taking the solution of the icon-based mental search to another level.

Getting this right taught me a lesson. 

> Don't parse ANSI escape codes with regex

My first several attempts tried to strip `eza`'s color codes to re-style the first letter, and each one leaked a different fragment `(36m, 1;4m)` as literal text, because eza emits color and bold and underline codes and hand-parsing all of them was a losing game. The version that finally worked never strips anything, and instead reads through escape codes and inserts styling around just the first letter:

```perl
perl -pe 's/(\e\[[0-9;]*m)+\K([[:alnum:]])/\e[1;4m$2\e[22;24m/'
```

`\K` tells perl to keep the matched color codes untouched and only wrap the first letter; `22;24` resets bold and underline without killing eza's color.

### Git you can read faster.

Interactive rebase is where a lot of people (including me) get lost. The `pick`/`reword`/`squash`/`drop` list is powerful and completely undifferentiated by default, since every command has the same color. So I color-coded them by meaning: green `pick` (keep), red `drop` (delete), purple `squash` (fold up), and so on. It's a gitrebase `FileType` autocmd in Neovim that matches each command word and paints it at a priority high enough to beat treesitter's:

```lua
vim.fn.matchadd("RebaseDrop", "\\v^(d|drop)>", 200)  -- red
```

Suddenly the plan reads like a plan instead of a wall of identical verbs. Merge conflicts get the same treatment via `git-conflict.nvim`, which shades the two sides and lets me resolve with a keystroke instead of hand-matching `<<<<<<<` markers.

## A "gotcha" from Neovim 0.12

If you're on Neovim 0.12 and your treesitter setup is crashing or your parsers silently aren't installing, here's the thing that cost me an evening: `nvim-treesitter`'s main branch is now required, and it has a completely different API. Don't do `ensure_installed` in a setup() call. Instead:

```lua
require("nvim-treesitter").install({ "lua", "python", "rust", ... })
```

...plus a `FileType` autocmd that calls vim.treesitter.start() per buffer, because highlighting isn't auto-enabled anymore. 

Two more traps I hit: the `git_rebase` parser and the `gitrebase` filetype have different names and you have to register the mapping yourself with `(vim.treesitter.language.register("git_rebase", "gitrebase"))`, and Telescope's previewer will crash with a languagetree error unless you disable treesitter in the preview. If you've been fighting any of these, that's the fix.

## The small tools that compounded immensely

None of these are novel, but together, they made the difference between friction and flow for my work setup:

- `atuin` — Ctrl-R history that's actually searchable, with timing and context. I stopped memorizing commands and started just... finding them.
- `zoxide` — z \<part-of-directory-name\> jumps to a frecent directory that starts with the name part. With thirty projects, this beats any listing. Example: z ra will lead me to the random-project directory if I frequent it a lot.
- `fzf` — fuzzy everything.
- `zsh-syntax-highlighting` — colors my input as I type (dim args, green commands, cyan paths, red typos), so the command line reads differently from program output.
- `yazi` - goated interactive file manager, shows images, PDFs etc. in terminal and a breeze to navigate

## What I actually took from this

Two things.

First, most of my time went into fighting layers that emit their own formatting. The fixes that worked all shared a shape: stop wrestling the layer, look up directly what you need, or insert around its output instead of tearing through it. Lowkey an insane debugging instinct I shall carry forward.

Second, a terminal is a tool, it needs to work like a usable one. I must be able to use it to make building/shipping projects faster and not the other way around. Everything that makes it slower is a problem that needs to be fixed about the tool.
